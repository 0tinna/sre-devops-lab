## 本次实际踩到并修掉的两个问题（面试可直接讲）

**1. kube-state-metrics 永远 0/1 NotReady**

Probe 报 404。用临时 busybox Pod 直连 Pod IP 逐端口逐路径探测，得出实测端点分布：

```text
8080 (http-metrics): /healthz 200, /livez 200, /readyz 404
8081 (telemetry)   : /readyz 200, /healthz 404, /livez 404
```

就绪探针写成了 `8081/healthz`，该路径不存在。改成 `telemetry/readyz` + `http-metrics/livez` 后恢复正常。

**2. 5xx 比例告警永远不触发（真实缺陷）**

注入 720 次 500，Prometheus 里 5xx 比例只有 0.0006。查区间数据发现计数器在跳：

```text
53536 → 53538 → 66702 → 66703 → 53542 → 66708 ...
```

12 个采样点 3 次回退。根因：gunicorn 2 个 worker，`prometheus_client` 没开 multiprocess，
`/metrics` 每次只返回命中的那个 worker，Prometheus 看到伪 reset，`rate()` 失真（算出 1366 req/s，
真实探针速率约 0.1 req/s）。修复已落代码。

顺带修正表达式：5xx 比例的分母排除 `/healthz|/readyz|/metrics`，
否则探针高频 200 会把业务错误率从 100% 稀释到 77%。

## 面试表述（更新版）

> 我在 1 master + 1 worker 的 Kubernetes 实验环境上，把 Flask 服务从代码做到可部署可观测。
> CI 用 GitHub Actions 跑单测、构建镜像推 GHCR；Deployment 配 readiness/liveness、资源限制和非 root 上下文，
> `maxUnavailable: 0` 保证坏发布不中断服务。监控侧没有引 Operator，用 pod 注解 + `kubernetes_sd_configs`
> 做服务发现，省掉 3 个 CRD 和一组 controller，代价是 relabel 自己写；10 条告警规则覆盖可用性、
> 错误率、延迟、重启和容量，并且**真的触发过**——我用 `command: /bin/false` 造 CrashLoop，
> 看到 `TargetDown` 和 `PodRestartTooOften` 进入 Firing、Alertmanager 收到，`rollout undo` 后自动 resolved。
>
> 调度上做了取舍：工作节点只有 3.6 GiB，监控栈全部 nodeSelector 到带 NoSchedule taint 的 master，
> 配 toleration，总请求 290m/608Mi。
>
> 两个真实故障：一是 kube-state-metrics 就绪探针写成 `8081/healthz`，该端口只有 `/readyz`，
> 导致 Pod 永远 NotReady、Service 无 Endpoint，我用临时 Pod 直连 IP 逐端口探测确认后修正；
> 二是 gunicorn 双 worker 下 `prometheus_client` 没开 multiprocess，计数器在 worker 间来回覆盖，
> Prometheus 看到伪 reset，`rate()` 算出 1366 req/s 而真实值约 0.1，5xx 比例告警永远不触发——
> 从 `query_range` 的数据回退里定位到根因，改用 `MultiProcessCollector` + 共享 emptyDir 修复，
> 同时把错误率表达式的分母剔掉探针端点，避免高频 healthz 稀释业务错误率。
